# WP-045: Deploy und Rollback über die Warteschlange des Server-Verbunds

## Ziel
Release und Rollback starten prod nicht mehr per ssh, sondern als Lauf des Nomad-Jobs `deploy-poker` des Server-Verbunds (fleet #13, #19): Log und Ergebnis in Nomad und Grafana, nie zwei Läufe zugleich, Rollback ein Befehl (D-039).

## Scope
**Drin:**
- `scripts/deploy_job.sh deploy|rollback [<commit>]` nach dem Vertrag des Verbunds (fleet README Abschnitt 2a)
- `scripts/fleet-deploy.sh`, `npm run prod:deploy` / `prod:rollback`
- `release.sh` deployt über den Job; Rollback-Hinweis in `release-verify.sh`
- Tests `scripts/test/deploy-job.test.mjs`, angepasst `release-verify.test.mjs`
- Doku: OPERATIONS („Deploy-Job“, Release, Rollback), ARCHITECTURE, README, WORKFLOW, D-039 (mit der Begründung, warum Tische im Server-Prozess bleiben)

**Nicht drin:**
- Vorlage `deploy-poker` und `jobs/deploy.sh` (fleet-Repo, `deploy.toml`)
- Release (`npm run release`, Arthur) – erst danach liegt `deploy_job.sh` auf dem Studio
- Tische oder Bots als eigene Nomad-Jobs (D-039: bleiben im Server-Prozess)

## Akzeptanzkriterien
- [x] `deploy_job.sh`: Deploy ohne Commit baut aus `main`, mit Commit/Rollback detached, Tunnel mit `TUNNEL_TOKEN`, Exit 0/1/2/75 getestet
- [x] `release.sh` startet prod nicht mehr per ssh, Rollback-Hinweis über `prod:rollback`
- [x] Deploy und Rollback über Nomad auf mac-2 getestet (Test-Instanz mit eigenem Compose-Projekt und Port), danach aufgeräumt
- [x] D-039 in DECISIONS.md, OPERATIONS „Deploy-Job“
- [x] `npm run check` grün
